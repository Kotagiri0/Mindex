# Перенос харнесса КОРА в TypeScript/Node (продукт «Мысль»)

Адресат: Claude Code в репозитории продукта. Это не «перепиши Python на
TS» — это **перенос архитектуры и алгоритмов**, выстраданных живыми
багами (см. `experiment_03/RESULTS.md` и git-историю ветки
`claude/epic-cannon-jkgr43`). Каждый паттерн ниже сопровождается тем
живым багом, который он чинит — это не архитектурная мода, а
воспроизведённые и закрытые тестом провалы. Пропустишь паттерн — велика
вероятность отгрести тот же баг заново на новом стеке.

**Как использовать этот документ**: не переписывай его в TS-комментарии
дословно, но КАЖДЫЙ алгоритм переноси с той же логикой — особенно
регулярки и JSON-repair (раздел 3), там ошибка в один символ откатывает
защиту на ноль. Исходники для сверки — `kora/orchestrator.py`,
`kora/tools.py`, `kora/prompts.py` в этом репозитории (ветка
`claude/epic-cannon-jkgr43`).

## 0. Принцип, который держит всё остальное

**Дисциплина — в коде, не в промпте и не в весах.** Модели (маленькие
и большие, дообученные и нет) фабрикуют факты, выдумывают JSON-схемы,
обрывают генерацию на середине. Промпт — смягчение; гарантия — только
детерминированный код вокруг вызова модели. Все паттерны ниже — это
код, который не доверяет модели, а проверяет её вывод.

## 1. Формат вызова инструмента и системный промпт

### 1.1 Формат тега

```
<action tool="домен.метод">{"параметр": "значение"}</action>
```

Требования к парсеру (портируй все три ветки — каждая закрывает живой
провал конкретной модели):

1. **Основной формат** — regex с любыми кавычками вокруг `tool=`:
   ```js
   const ACTION_RE = /<action\s+tool=['"]([^'"]+)['"]\s*>([\s\S]*?)<\/action>/g;
   ```
2. **JSON в теле без атрибута** (модель иногда пишет
   `<полисад.remember>{"key":...}</полисад.remember>` вместо правильного
   формата) — без этой ветки действие тихо терялось, а модель
   рапортовала «сохранил», хотя вызова не было (худший класс провала —
   ложное подтверждение):
   ```js
   const TOOL_WORD = "[\\w\\p{L}]+\\.[\\w\\p{L}]+"; // ASCII + любой алфавит
   const BODY_ACTION_RE = new RegExp(
     `<(${TOOL_WORD})>\\s*(\\{[\\s\\S]*?\\})\\s*</\\1>`, "gu");
   ```
3. **Оборванный тег в конце вывода** — генерация упёрлась в лимит
   токенов ДО закрывающего `</action>`. Живой баг: модель (DeepSeek)
   сгенерировала огромный выдуманный JSON, обрыв на середине строки →
   основной regex требует закрытие → действие не распознаётся ВООБЩЕ →
   петля решает «действий нет, это финальный ответ» → пользователю в
   чат вываливается сырой `<action>{полстраницы JSON...`. Обязательная
   ветка:
   ```js
   const TRUNCATED_ACTION_RE =
     /<action\s+tool=['"]([^'"]+)['"]\s*>((?!<\/action>)[\s\S])*$/;
   ```
   Спасённый хвост уходит в JSON-repair (раздел 3) — сам он почти
   всегда невалиден (оборван на середине значения).

### 1.2 Канонизация имени инструмента

Модель путает `р`/`r` (кириллица/латиница похожи визуально), генерит
транслит и опечатки в методе. Канонизация по первой букве домена +
ключевым корням метода — не точное совпадение:

```
домен: р/r→рельса, п/p→полисад, н/n→навык, а/a→артефакт, с/s/c→сервис
метод: содержит "scrape"→scrape_url, "remember"|"store"→remember,
       "search"|"recall"→search, "slide"→slides, "site"|"page"→site,
       "call"→call, "load"|"get"→load, "list"→list
```

**Важно**: диспетчер должен вызывать инструмент по КАНОНИЧЕСКОМУ имени,
не по сырому — живой баг: смешанный алфавит (`rельса.search`, латинская
`r`) канонизировался правильно, но диспетчер получал сырое имя, которого
нет в реестре → «неизвестный инструмент», хотя весь смысл канонизации —
починить именно этот случай. Дедуп повторных вызовов — тоже по канону
(иначе `relsa.search` и `рельса.search` с одинаковыми аргументами не
считаются дублем и оба уходят в сеть).

### 1.3 Системный промпт — обязательный блок

Живой баг (воспроизведён трижды): модель без файнтюна на формат петли
(любая сильная API-модель — DeepSeek, GPT, Claude) **с уверенностью
придумывает свою JSON-схему** для инструментов, если формат не
задокументирован явно в системном промпте. Пример реального провала:
модель сгенерировала для инструмента презентаций
`{"width":1920,"height":1080,"theme":{...},"slides":[{"type":"title","content":{...},"style":{...}}]}`
вместо реального формата `{"title":"...","markdown":"..."}`.

**В прод-системник обязательно перенести блок, эквивалентный
`kora/prompts.py::DEFAULT_SYSTEM_PROMPT`**:
- список инструментов с точной JSON-схемой аргументов у каждого;
- пример правильного хода (вопрос → `<action>` → `[СТОП]` → `<result>` → `<answer>`);
- **явный анти-пример** («вот так делать НЕЛЬЗЯ» с конкретной неправильной
  схемой) — позитивного примера недостаточно, сильные модели его
  игнорируют в пользу «более богатой» придуманной схемы;
- правило честности: пустой/ошибочный результат → одна повторная
  попытка → затем честное «не нашёл», запрет выдумывать факты/ссылки.

Если в целевой системе есть навыки/сервисы — их каталог (имя+описание,
БЕЗ полной схемы) добавляется в промпт ДИНАМИЧЕСКИ по факту наличия
реестра, не хардкодится (иначе система обещает модели инструмент,
которого в рантайме нет).

## 2. Guardrails петли — что проверять после каждого вызова модели

Порядок в оригинале важен (первое совпадение решает), сохрани его:

| # | Guardrail | Живой баг, который чинит | Логика |
|---|---|---|---|
| 1 | **Анти-фабрикация `<result>`** | Модель дописывает в СВОЙ вывод поддельный `<result>` и отвечает по нему, будто инструмент уже вызван | Обрезать вывод модели по концу ПОСЛЕДНЕГО распознанного `<action>` перед тем, как класть в контекст истории; отдельно вырезать regex `<result\b[^>]*>[\s\S]*?<\/result>` из ЛЮБОГО текста модели перед показом пользователю — настоящий `<result>` вставляет только оркестратор |
| 2 | **Сырые теги не показываются пользователю** | Оборванный/непарсенный `<action>` вываливался в чат как «ответ» | Финальный ответ ВСЕГДА прогоняется через фильтр: если после извлечения `<answer>` в тексте остался `<action`, вырезать его regex-ом; если после вырезания пусто — честная заглушка «ответ оборвался», не пустое сообщение |
| 3 | **Дедуп вызовов** | Модель повторяет тот же вызов до исчерпания лимита шагов | Ключ = (канон.имя, JSON.stringify(отсортированных args)); повтор → блокировать с сообщением «уже вызывался, ответь по данным выше» |
| 4 | **Бюджет вызовов на инструмент за ход** | Модель сделала 25 поисков подряд за один ход | Лимит на инструмент (search~4, remember~3, дефолт 5); исчерпан → блок с явной инструкцией «сформулируй ответ по имеющимся данным» |
| 5 | **Remember-guard** | Модель сохраняла в долгую память ВЫДУМАННЫЕ факты/ссылки, не встречавшиеся в реальных результатах инструментов | Перед записью факта: (а) если в значении есть URL, которого не было ни в одном реальном результате инструмента и ни в словах пользователя — блок; (б) если факт вообще ничем не подтверждён (ни результатом, ни явной просьбой пользователя «запомни») — блок |
| 6 | **Write-payload guard** (для внешних действий) | Тот же класс, что remember-guard, но для отправки вовне: скраб убирал URL из ПОКАЗЫВАЕМОГО пользователю вопроса подтверждения, а по «да» уходил ОРИГИНАЛ с выдумкой — расхождение показанного и отправленного | Выдуманные URL в payload write-действия блокируют вызов ДО постановки в очередь на подтверждение, а не после |
| 7 | **Эскалация после серии провалов** | 5 шагов подряд пустых поисков — сотни секунд впустую, потом невнятный финал | 3 провала подряд (ошибка/пустой результат) → честный отказ БЕЗ обращения к модели («не смог найти данные»), не давать ещё один шанс |
| 8 | **Freshness-дозапрос** | Вопрос про свежие данные (курс, новости, версия) — модель ответила из головы без единого вызова инструмента | Regex-детектор маркеров свежести (`\b(новост|сейчас|сегодня|завтра|последн|свеж|актуальн|стоит|цена|курс|погод|верси|вышел|релиз)`, `\b` обязателен — иначе «курс» ловит «реКУРСию»); сработал + ноль ВЫЗОВОВ ДАННЫХ за ход (навык.load/сервис.list не считаются данными) → один принудительный дозапрос «вызови поиск сейчас», не более одного раза за ход |
| 9 | **Reinject задачи после ошибки** | Маленькие/слабые модели дрейфуют от исходного вопроса после ошибки инструмента, начинают отвечать не на то | Если в шаге была хотя бы одна ошибка инструмента — добавить в контекст явное напоминание исходного вопроса пользователя |
| 10 | **Компакция контекста** | Полный JSON результата инструмента нужен модели ровно один шаг; дальше он баллас-контекст, который ядро пересчитывает на каждом шаге | Результаты ПРОШЛОГО шага (не текущего) сжимаются до выжимки (заголовки/URL/ошибки), полный JSON остаётся только у свежего шага; отдельно копится несжимаемый evidence-буфер для guardrails 1/5/6 |
| 11 | **Санитизация спецтокенов** | Скрейпленный веб-контент может содержать chat-template спецтокены модели (`<\|im_start\|>` и т.п.) — инъекция через контент, который не контролируется | Вырезать regex `<\|[a-zA-Z_]+\|>` из ЛЮБОГО текста, который идёт в контекст модели из внешнего источника (веб, документы) |
| 12 | **Санитизация в `describe`-вопросе гейта** | Payload вопроса подтверждения может содержать спецтокены из выдуманного/скрейпленного текста | Тот же фильтр применяется к тексту, который показывается пользователю в вопросе «подтвердить?» |

## 3. JSON-repair (переносить максимально точно)

Модели генерируют почти-валидный JSON: висячие запятые, одинарные
кавычки, текст вокруг объекта, обрыв на середине (в т.ч. **внутри
строкового значения** — живой случай: `"backgroundColor": "#` и конец
вывода). Наивный подсчёт `{`/`}` без учёта, внутри ли мы строкового
литерала, — ломается на первом же `{`/`}` внутри строкового значения
(`{"query": "search for {x}"}`) и не может закрыть обрыв,
случившийся посреди незакрытой строки.

Алгоритм (два прохода, оба **строково-осознанные** — отслеживают
`in_string`/`escape` с учётом `\"`):

**Проход 1 — найти границу первого объекта** (`findBalancedObject`):
идти от первого `{`, считать глубину `{`/`}`, ИГНОРИРУЯ их, если
находимся внутри строки. Глубина дошла до 0 → вернуть срез. Не дошла
до конца текста → вернуть остаток как есть (это обрыв, чинить дальше).

**Проход 2 — дозакрытие** (`closeUnterminated`): та же строково-
осознанная сканировка, но со **стеком** открывающих `{`/`[` (не просто
счётчиком!) — живой баг: счётчик `{`/`}` закрывал объекты, но
незакрытый МАССИВ (`"slides": [{...}, {...}` без закрывающего `]`)
оставался невалидным даже после дозакрытия объектов, потому что стек
нужен для правильного ПОРЯДКА закрытия и правильного ТИПА скобки.
В конце: если сканировка закончилась внутри строки — сначала добавить
закрывающую кавычку, ПОТОМ закрыть стек скобок в обратном порядке
(LIFO), сопоставляя `{`→`}`, `[`→`]`.

```
repair(raw):
  frag = findBalancedObject(raw)
  if frag is null: return null
  try: return JSON.parse(frag)          # повезло, сразу валиден
  catch: pass
  fixed = frag
  if !fixed.includes('"'): fixed = fixed.replaceAll("'", '"')  # только если НЕТ двойных кавычек вообще — не портим валидные строки
  fixed = closeUnterminated(fixed)      # строка → скобки, в этом порядке
  fixed = fixed.replace(/,\s*([}\]])/g, "$1")  # висячая запятая
  try: return JSON.parse(fixed)
  catch: return null
```

Тест-кейсы, которые обязаны проходить (взять как есть из
`kora/selftest.py`, раздел "JSON-repair"):
- `{'query': 'x', 'limit': 3}` → одинарные кавычки чинятся
- `{"query": "x",}` → висячая запятая
- `вот запрос: {"query": "x"} мусор` → текст вокруг вырезается
- `{"query": "x"` → дозакрытие
- `{"a": {"b": "text` → вложенный обрыв внутри строки: закрыть кавычку, потом два `}`
- `{"a": "text with { and }"` → `{`/`}` внутри строки не путают глубину
- глубоко вложенный JSON с `"slides": [{...}, {...}, {"style": {"color": "#` (обрыв внутри строки третьего уровня вложенности, незакрытый массив) → должен восстановиться в валидный объект с массивом `slides` из уцелевших элементов

## 4. Coerce чужой JSON-схемы (для «производящих» инструментов)

Даже с идеальным промптом (раздел 1.3) сильные модели ИНОГДА игнорируют
формат и присылают свою схему. Вместо отказа — попытка восстановить
целевой формат из типичных альтернативных структур. Живой пример
(презентации): вместо `{"title","markdown"}` модель прислала
`{"slides":[{"type":"title","content":{"title":"...","subtitle":"..."}}]}`.

Правило: если целевого поля (например `markdown`) нет, но есть массив
известного альтернативного имени (`slides`, `sections`, `blocks`,
`pages[].sections`) с элементами, у которых угадываются `title` +
(`content`|`body`|`items`) — собрать целевой контент из них
программно. Не универсально для любой мыслимой схемы — закрывает
конкретный наблюдаемый класс, расширяется по мере появления новых
живых случаев. Держи эту функцию как growing whitelist, не как попытку
объять все возможные структуры сразу.

## 5. HITL-гейт для write-действий

Читать мир агент может свободно; ДЕЙСТВОВАТЬ вовне (отправить
сообщение, создать событие, вызвать вебхук) — только с явного согласия
пользователя. Механика:

1. Действие с флагом `write: true` в манифесте (раздел 6) НЕ
   исполняется сразу — откладывается в pending-очередь, привязанную к
   `(userId, threadId)` (НЕ только userId — живой баг: «да» в другом
   треде/чате подтверждало действие из другого).
2. Ход завершается вопросом: **точный payload действия рендерится
   кодом из pending-объекта**, не пересказом модели — модель может
   «прилизать» инъецированную часть payload при пересказе. Показанное
   должно byte-in-byte совпадать с тем, что уйдёт по подтверждению.
3. Несколько write-действий в одном шаге модели → ВСЕ собираются в
   ОДИН pending и один вопрос — живой баг: при обработке по одному
   второе действие молча терялось, а ответ «Готово» ложно подтверждал
   его исполнение.
4. Мультиэкшн-шаг (write вперемешку с read/поиском) → гейт проверяется
   ПРЕ-ПАССОМ по всем действиям шага ДО исполнения любого из них — живой
   баг: если сначала исполнить поиск, а потом упереться в гейт,
   результат поиска терялся при досрочном возврате.
5. Ответ пользователя: строгий regex на «да»/подтверждающие слова
   исполняет; строгий regex на «нет»/отмену — сбрасывает; ЛЮБОЙ другой
   ответ тоже сбрасывает pending (смена темы = не согласие, молча
   слать вдогонку нельзя) и обрабатывается как новое сообщение.
6. **TTL 15 минут** — «да» спустя час не согласие на забытое действие.
7. Permissions поверх гейта — правила вида `"сервис:действие(арг=знач)"`
   (скоуп по конкретному значению аргумента, не просто по имени
   действия — «разрешить send_message» без скоупа = разрешение слать
   КОМУ УГОДНО). Порядок: **deny → allow → ask**, deny всегда сильнее
   более широкого allow, первое совпадение решает.
8. Append-only аудит-лог каждого события гейта (poставлен на
   подтверждение / подтверждено / отклонено / протухло / авто-разрешено
   / запрещено политикой) — включая отклонённые и протухшие, это самый
   ценный сигнал для последующих регрессий и построения allow-листов.

## 6. Интеграции — манифест, а не код на сервис

Проблема: интеграций сотни, харнесс один. Решение (уже проверено):
**интеграция = декларативный манифест (JSON/YAML), не код**. Один
универсальный HTTP-исполнитель на ВСЕ сервисы; модели видны два
инструмента: `список_сервисов` и `вызвать_сервис(service, action, args)`.

Манифест: `base_url`, схема авторизации (подстановка токена в URL /
bearer-заголовок / произвольный заголовок), список действий с
`required`/`optional` полями, опциональной мини-JSON-схемой параметров
(`type`, `enum` — валидируются ДО HTTP-вызова), флагом `write`.

Правила исполнителя:
- секрет — только ИМЯ в манифесте (`"credential": "telegram_bot_token"`),
  значение приходит из внешнего хранилища per-user, никогда не в
  манифесте и никогда не попадает в контекст модели;
- таймаут ~30с;
- retry с паузой — **только read-действия**, только на сетевые
  ошибки/5xx/429 (write без idempotency-ключа НЕ ретраить — письмо
  уедет дважды);
- тело ошибки усечено (~500 симв) — модели нужен статус и суть, не
  мегабайт HTML от прокси;
- секрет вычищается из текста ЛЮБОЙ ошибки перед возвратом (сетевые
  исключения иногда вшивают URL целиком, включая токен из
  `token_in_url`-авторизации) — заменить на `•••`;
- в исходящий запрос уходят ТОЛЬКО объявленные в манифесте поля —
  лишнее из аргументов модели отсекается.

## 7. Оркестрация: декомпозиция → параллель → синтез

Паттерн orchestrator-workers (Anthropic, «Building effective agents»).
Для СОСТАВНЫХ целей («сводка по трём проектам», «сравни X и Y») один
линейный проход либо теряет части задачи, либо мешает их контексты.

1. **Детектор составности** — консервативный regex по русским маркерам
   (сводка/дайджест/«по каждому»/«сравни А и Б»/явный нумерованный
   список в сообщении пользователя). Ложное срабатывание стоит 3+
   лишних вызова модели вместо одного — при сомнении НЕ запускать,
   падать в обычную петлю.
2. **Планировщик** — отдельный вызов модели, строгий формат вывода
   (только нумерованный список, 2–4 пункта, потолок ширины — план
   длиннее почти всегда шум). Парсинг regex `^\s*\d+[.)]\s+(.+)$`
   построчно. Меньше 2 пунктов распарсилось → тихий откат на обычную
   петлю (штатный путь, не ошибка).
3. **Параллельное исполнение подзадач** — каждая своим суб-агентом с
   ЧИСТЫМ контекстом (не видит истории диалога и соседних подзадач),
   коротким лимитом шагов (подзадача уже атомарна). Suq-агент НЕ имеет
   доступа к write-интеграциям (не может задать вопрос подтверждения
   из параллельного потока) и не имеет своей вложенной декомпозиции.
   Использовать `Promise.allSettled`-эквивалент с обновлением статуса
   узла СРАЗУ по завершении каждой подзадачи (не ждать всех разом) —
   живой граф прогресса должен быть живым, не пост-фактум.
4. **Синтез** — отдельный вызов модели собирает результаты в один
   ответ. Провалившиеся/пустые подзадачи явно помечаются «ПРОВАЛЕНА» в
   промпте синтеза — модель обязана честно сказать, какой части не
   хватает, не выдавать частичный результат за полный. Синтезированный
   ответ проходит ТЕ ЖЕ guardrails, что обычный (анти-фабрикация,
   скраб непроверенных URL по совокупному evidence всех подзадач).

## 8. Живой граф процесса (для UI)

Ключевой урок по UX (не архитектурный, но важный): **граф должен
показывать ЛЮБОЙ ход, не только декомпозированный**. Изначальная версия
вела граф только для оркестрации — 99% реальных запросов (простая
линейная петля) не показывали пользователю вообще ничего, пока не
придёт финальный ответ. Это выглядит «не по-агентному».

Модель узла: `{id, label, status: queued|running|done|failed, detail,
thought}`. `thought` — разворачиваемое содержимое (что показывать по
клику): извлечённое размышление модели (`<think>` или проза до
действия) + краткая сводка результата инструмента. Узлы обновляются
ЖИВЬЁМ по ходу выполнения (не одним снапшотом в конце), и **цепочка
узлов прикрепляется к КОНКРЕТНОМУ сообщению в истории переписки**, не к
отдельному блоку, который затирается следующим ходом — иначе
пользователь не может вернуться и посмотреть, что происходило в
прошлом ответе.

## 9. Вложения для не-мультимодального ядра

Если основная модель текстовая (не видит изображения) — два раздельных
пути обработки, не один:
- **Текстовые форматы** (PDF с текстовым слоем, TXT) — извлекать текст
  НАПРЯМУЮ библиотекой, без LLM: дешевле и надёжнее OCR через
  мультимодалку. PDF-скан без текстового слоя — честная ошибка с
  подсказкой, не попытка выдать пустоту за содержимое.
- **Картинки (и сканы без текстового слоя)** — один STATELESS вызов
  дешёвой мультимодальной модели (без истории диалога — просто «вот
  файл, опиши»). Результат подставляется основной модели как
  `<result>` обычного инструмента — пользователь не видит сырой вызов
  зрения, видит только финальный ответ основной модели, опирающийся на
  описание.
- Описание вложения подмешивается в то, что видит МОДЕЛЬ, но НЕ в
  историю переписки, которую видит пользователь, — в чате остаётся
  чистый текст пользователя + чип с именем файла, не полный рассказ
  мультимодалки.

## 10. Навыки — процедуры вне промпта и вне весов

Слой поверх фактов (веб) и памяти (пользователь): процедуры «как
делать» как внешние модули, не хардкод в промпте. Формат: файл с
фронтматтером `name`+`description` (лимиты: name ≤64 симв,
description ≤1024) + тело-инструкция.

Discovery — КАТАЛОГ (имя+описание каждого навыка) инъецируется в
системный промпт ВСЕГДА, полное тело — по запросу через отдельный
вызов. Живой урок: если полагаться только на «инструмент списка
навыков», который модель должна ДОГАДАТЬСЯ вызвать в нужный момент —
она не догадывается (особенно маленькие модели, но и большие
пропускают). Каталог перед глазами — это узнавание, а не вспоминание.
