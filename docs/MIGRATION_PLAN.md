# План переноса харнесса в облако (тестовый сервер → прод)

Статус на июль 2026. Петля и слои готовы и покрыты 238 тестами
(`python -m kora.selftest`, без сети и GPU), но это исследовательская
упаковка: один пользователь, SQLite-файл, состояние в процессе. Этот
документ — что и в каком порядке переносить, чтобы получить сначала
облачный тестовый сервер, потом интеграцию в прод «Мысли».

## Что уже зарекомендовало себя (переносится КАК ЕСТЬ)

Проверено бенчмарком experiment_03 (см. `experiment_03/RESULTS.md`:
sreda_tools 0.75 A+B+C против hermes_bare 0.12 — инструменты дают ×13,
harness-эффект подтверждён на трёх семействах моделей) и двумя волнами
адверсариального ревью (16 багов найдено и закрыто тестами).

| Компонент | Где | Ценность |
|---|---|---|
| ReAct-петля с guardrails | `kora/orchestrator.py` | дисциплина в коде, не в весах: анти-фабрикация `<result>`, remember-guard, бюджеты/дедуп вызовов, эскалация после 3 провалов, компакция контекста, санитизация спецтокенов, JSON-repair (строково-осознанный, чинит оборванную генерацию) |
| Оркестрация | там же | декомпозиция → параллельные субагенты → синтез, живой граф задач с thought-узлами |

## Фаза 0 — тестовый сервер (ГОТОВО этим коммитом)

`Dockerfile` + `run_server.py`: RouterAI-модели, конфиг из env
(`.env.example`), Basic-auth обязателен для не-localhost, память и аудит
в volume `/data`, selftest гоняется при сборке образа.

```bash
docker build -t kora-server .
docker run -p 8765:8765 -e ROUTER_API_KEY=... -e KORA_UI_PASSWORD=... \
    -v kora-data:/data kora-server
```

Ограничения фазы (осознанные): один пользователь, SQLite в volume,
состояние теряется при потере volume. Для закрытого теста — достаточно.

## Фаза 1 — прод-системник и персона (1-2 дня)

Харнесс спроектирован под подмену промпта: `Kora(system_prompt=...)` —
`DEFAULT_SYSTEM_PROMPT` это фолбэк для моделей без файнтюна, НЕ прод-текст.

- [ ] Взять из прод-репо системный промпт «Мысли» (персона, тон, правила
      продукта) и подать как `system_prompt`. ВАЖНО: сохранить в нём
      документацию формата `<action>` — блок «БАЗОВЫЕ ИНСТРУМЕНТЫ …
      ФОРМАТ ВЫЗОВА» из `kora/prompts.py` вставить в прод-промпт как есть
      (живой урок: модель без этого блока выдумывает свою JSON-схему).
- [ ] Профиль пользователя: `Memory.profile()` сейчас исследовательский —
      заменить на прод-источник (профиль юзера «Мысли»).
- [ ] Прогнать `experiment_03/runner.py --config <модель>_tools` с
      прод-промптом — регрессия качества до/после подмены.

## Фаза 2 — state в Supabase (ядро переноса, ~1-2 недели)

Всё локальное состояние — на Postgres. Логика НЕ меняется, меняются
адаптеры хранения:

- [ ] `polisad/store.py` (SQLite) → таблицы в Supabase + pgvector вместо
      локальных sentence-transformers эмбеддингов. Интерфейс Store
      сохранить — Memory/каскад не трогаются.
- [ ] `Kora._history` (dict в памяти процесса) → таблица `dialog_history`
      (user_id, thread_id, role, content, ts). Читать хвост при run().
- [ ] `Kora._pending` (гейт) → таблица с TTL — иначе рестарт процесса
      теряет неподтверждённые действия.
- [ ] `audit_path` (JSONL) → append-only таблица `audit_log` (поля уже
      совместимы: ts/user/thread/event/details).
- [ ] permissions (dict в конструкторе) → таблица `permissions`
      (user_id, rule, expires_at); формат правил готов —
      `сервис:действие(арг=знач)`, deny>allow>ask.
- [ ] Артефакты: файлы → Supabase Storage, `/artifacts/<имя>` → signed URL.
- [ ] `relsa` global `_CACHE` → без изменений (пер-процессный кэш ок) или
      Redis, если инстансов несколько.

## Фаза 4 — производительность и экономика (~неделя)

- [ ] Раздельные модели: оркестратор (план/синтез) на сильной, субагенты
      на дешёвой. Точка врезки одна: `_run_sub` в orchestrator.py:562
      берёт `self.generate` — добавить `Kora(subagent_generate=...)`.
      По расчёту юнит-экономики это ~55% экономии на оркестрации.
- [ ] Prompt caching RouterAI/провайдера: системка ~1.2-1.4к токенов
      идентична во всех вызовах — кандидат №1 по цене (вход доминирует).
- [ ] Петля синхронная — для Telegram-бота обернуть в воркер-очередь
      (по потоку/таске на диалог). Полный async-рефакторинг НЕ нужен
      для старта: I/O-bound вызовы уже параллелятся ThreadPool-ом.

## Фаза 5 — наблюдаемость (параллельно фазам 2-4)

- [ ] Метрики из audit_log + stop_reason (уже логируются): steps/run,
      tool error rate по инструментам, loop rate, HITL acceptance rate
      (падение = агент предлагает чушь — самый дешёвый прокси качества).
- [ ] Golden-траектории: 30-50 реальных диалогов из аудита → реплей-
      регрессия перед каждым изменением промпта/скилла/модели
      (инфраструктура судейства уже есть: experiment_03/judge.py).

- `experiment_01..03`, `dataset/`, `finetune/` — исследования; результаты

- `webui` как прод-фронт — это дев-инструмент и референс UI-паттернов.

## Риски

1. **Промпт-дрифт**: прод-системник может конфликтовать с форматом
   инструментов → фаза 1 требует бенчмарк-регрессию, не «на глаз».
2. **Модели без файнтюна игнорируют формат** (доказано DeepSeek-ом
   трижды): защита в коде уже стоит (coerce, спасение обрывов), но новые
   модели = новые классы провала → держать selftest-паттерн «живой баг →
   тест → фикс».
3. **SQLite→Postgres**: каскад памяти чувствителен к качеству поиска —
   сравнить recall стемминг-яруса на реальных данных до/после.
4. **Один RouterAI на всё** — единая точка отказа; в манифесте задач
   фазы 4 предусмотреть фолбэк-провайдера в router_adapter.
