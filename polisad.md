# ПОЛИСАД — Система персональной памяти для AI-агентов

> Версия документа: 1.0 — 2026-06-11
> Статус: внутренняя техническая декларация
> Контекст: технология разработана внутри продукта Mindex, проходит боевую проверку в проде

---

## Что такое ПОЛИСАД

ПОЛИСАД — это многослойная система долгосрочной персональной памяти для AI-агентов. Технология решает фундаментальную проблему LLM: модели stateless по природе — каждый новый разговор начинается с нуля. ПОЛИСАД делает агента персональным: он помнит, накапливает контекст и умнеет от взаимодействия к взаимодействию.

**Ключевой принцип:** retrieval без LLM. Вся работа с памятью — математика и детерминированные структуры. LLM получает уже готовый, релевантный контекст и тратит токены только на генерацию ответа.

---

## Архитектура — три слоя памяти

### Слой 1: Профиль пользователя (Personal Profile Layer)
**Тип:** всегда присутствует в промпте, без условий  
**Источник:** треды с `title = 'О себе'`, `label = 'profile'`, или `source = 'заметка'` с title содержащим "себ"  
**Механика:** при каждом запросе к агенту — первые три профильных треда всегда инжектируются в системный промпт в блок `## Что пользователь рассказал о себе`  
**Стоимость:** SQL-запрос, 0 LLM-токенов на retrieval

Это не RAG — это постоянная идентичность пользователя внутри агента. Агент всегда знает кто перед ним.

---

### Слой 2: Семантическая память (Semantic Memory Layer / RAG)
**Тип:** динамический, по релевантности к текущему запросу  
**Источник:** все значимые треды пользователя с `summary IS NOT NULL` и `is_meaningful = true`  
**Механика поиска (каскадная):**

1. **Vector search** (если pgvector доступен)
   - Генерируем эмбеддинг последнего сообщения пользователя через `text-embedding-3-small`
   - Cosine similarity по всем тредам пользователя
   - Порог: `1 - (embedding <=> query_vector) > 0.65`
   - Возвращаем топ-3 по близости
   - Модель: `openai/text-embedding-3-small` через RouterAI

2. **Keyword fallback** (если vector miss или pgvector недоступен)
   - Извлекаем ключевые слова из последнего сообщения (слова > 3 символов, топ-5)
   - `ILIKE` по полям `title` и `summary`
   - Возвращаем топ-3 по `updated_at DESC`

3. **Recent fallback** (если keyword miss)
   - Последние 3 значимых треда пользователя
   - Используется только для фонового контекста, источники не показываются пользователю

**Инжект в промпт:** блок `## Из архива пользователя` с найденными summary  
**Источники:** показываются пользователю только при явном совпадении (vector или keyword hit), не при fallback  
**Стоимость:** 1 embedding API call + 1-2 SQL запроса, 0 LLM-токенов на retrieval

---

### Слой 3: Временная память (Temporal Memory Layer)
**Тип:** специфично для Telegram-бота, дневной цикл  
**Источник:** дневной тред бота `"Telegram Bot YYYY-MM-DD"`  
**Механика:**
- При каждом сообщении в боте: загружаем тред за сегодня из БД
- Передаём последние `CONTEXT_WINDOW = 50` записей как chat history
- После ответа: сохраняем обновлённый тред обратно в БД
- При создании нового дневного треда: вчерашний тред асинхронно саммаризируется
- Вчерашний summary инжектируется в промпт как `## Вчера в боте` — отдельным блоком, исключён из RAG

**Стоимость:** 2 SQL запроса (load + save), 0 LLM-токенов на retrieval текущего дня

## Саммаризация — как память создаётся

Память не существует без саммаризации. Это единственный этап где используется LLM.

### Триггеры саммаризации:
1. **При закрытии треда** (веб-чат) — если у треда нет summary и ≥2 сообщений от пользователя
2. **При создании нового дневного треда** (бот) — вчерашний тред саммаризируется если meaningful messages ≥ 4
3. **При сохранении заметки** — заметка сразу получает summary (сам текст заметки)
4. **Backfill** — `/api/admin/backfill-embeddings` для треды без эмбеддингов

### Процесс саммаризации:
1. Фильтруем диалог: только `role = 'user'` и `role = 'assistant'`, без tool_calls
2. Отправляем в LLM (deepseek/deepseek-v4-flash, max_tokens: 600, temperature: 0.2)
3. Получаем JSON: `{ is_meaningful: bool, summary: string }`
4. Структура summary: **Суть** (1 предложение) + **Ключевые тезисы** (2-4 буллета) + **Задачи** (если были)
5. `is_meaningful = false` → тред помечается, в RAG не участвует (small-talk, тесты)
6. Параллельно (fire-and-forget): генерируем эмбеддинг `title + summary` → сохраняем в pgvector

### Цена саммаризации:
- ~600 input tokens (диалог) + ~200 output tokens (summary) ≈ 800 токенов на тред
- Происходит один раз на тред, не повторяется
- Не блокирует пользователя — async

## Хранилище

**База данных:** PostgreSQL  
**Таблица:** `user_threads`

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | UUID | Идентификатор треда |
| `user_id` | TEXT | Владелец |
| `title` | TEXT | Название ("О себе", "Telegram Bot 2026-06-11", etc.) |
| `messages` | JSONB | Полная история сообщений |
| `summary` | TEXT | Сжатая память треда |
| `is_meaningful` | BOOLEAN | Флаг участия в RAG |
| `embedding` | vector(1536) | Эмбеддинг для vector search |
| `label` | TEXT | Системные метки ('profile', 'skill:self_knowledge') |
| `source` | TEXT | Источник ('мысль', 'заметка', 'telegram') |
| `updated_at` | BIGINT | Для сортировки по актуальности |

**Индекс:** HNSW на `embedding` для ANN-поиска  
**Расширение:** pgvector (опционально — система деградирует до keyword search без него)

## Текущие слабые места

### 1. Саммаризация — единственная зависимость от LLM
**Проблема:** LLM используется для создания summary. Это значит: задержка, стоимость, риск отказа провайдера, возможные галлюцинации в summary.  
**Масштаб:** при 1000 DAU с активным использованием — 1000 LLM-вызовов в сутки только на саммаризацию.

### 2. Нет промежуточной саммаризации внутри дня
**Проблема:** CONTEXT_WINDOW = 50 записей. При очень активном использовании бота (голосовые + тул-коллы) утренний контекст выпадает к вечеру.  
**Симптом:** бот переспрашивает то о чём уже говорили в этот же день.

### 3. Триггер саммаризации — закрытие треда
**Проблема:** пользователь не закрыл тред → summary не создан → тред не попадает в RAG при следующих запросах в других тредах.  
**Симптом:** "не помнит сегодняшний разговор" при переходе в новый тред.

### 4. Нет метрик
**Проблема:** мы не знаем RAG hit rate, среднюю similarity, % тредов с summary, качество саммаризации.  
**Следствие:** улучшать систему вслепую.

### 5. Размазанность по коду
**Проблема:** вся логика ПОЛИСАД размазана по обработчикам в `server.ts` и `server-bot.ts`. Нет единого модуля, нет чистого API, нет изоляции.

### 6. Эмбеддинги через RouterAI
**Проблема:** `text-embedding-3-small` вызывается через внешний провайдер (routerai.ru). Единая точка отказа для всей векторной памяти.

## Что работает хорошо

- **Каскадный поиск** (vector → keyword → recent) — graceful degradation, система никогда не падает
- **Профиль всегда в промпте** — агент знает кто пользователь без запросов
- **is_meaningful фильтр** — мусорные треды не засоряют память
- **pgvector опционален** — система работает без него через keyword search
- **Fire-and-forget эмбеддинги** — не блокируют пользователя
- **Отдельный блок "Вчера в боте"** — вчерашний контекст не смешивается с RAG

## Потенциал как B2B API

ПОЛИСАД решает задачу которая есть у любого разработчика AI-агентов:
- Как дать агенту долгосрочную память?
- Как сделать её персональной?
- Как не тратить токены на retrieval?

Публичный API мог бы выглядеть так:
```
POST /polisad/context     → { userId, query } → готовый контекстный блок для промпта
POST /polisad/remember    → { userId, threadId, messages } → саммаризация и сохранение
GET  /polisad/profile     → { userId } → профиль пользователя
POST /polisad/search      → { userId, query } → поиск по архиву
```

Целевая аудитория: разработчики Telegram-ботов, корпоративных AI-ассистентов, персональных агентов.

## Философия в контексте декларации лаборатории

ПОЛИСАД — живое воплощение принципа "компьютер внутри LLM":
- **Жёсткий диск** — PostgreSQL + pgvector хранит и извлекает, без LLM
- **Адресация** — косинусное расстояние как указатель в памяти
- **Только CPU** — LLM получает уже смонтированный контекст

Система создана органически внутри продукта Mindex и прошла боевую проверку. Это не концепт — это работающая технология в проде.
